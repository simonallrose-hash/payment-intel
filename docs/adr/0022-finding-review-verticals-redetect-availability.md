# ADR-0022 — Ревью находок, вертикали, повторная детекция и события доступности

Статус: принято (этап 4). Связано: FR-QA-05, FR-DT-10, FR-DT-12, FR-SC-05, FR-HI-03, ADR-0006, ADR-0020.

## Решения

1. **Ревью находки пишет gold-метку (FR-QA-05).** Подтверждение и отклонение
   провайдера или способа оплаты на магазине — это `gold_label`
   (`present=true/false`) от аналитика, поэтому ручной разбор пополняет gold
   set без отдельного импорта (ADR-0006: метки только от аналитика).
   Очередь упорядочена по возрастанию уверенности; улики — последние
   наблюдения из ClickHouse (сигнал, страница, правило, ключ скриншота).
2. **Отклонённая находка подавляется, а не удаляется.** Поле `suppressed`
   на `store_provider` / `store_payment_method` скрывает строку из API,
   фильтров поиска, экспортов и отчётов до повторного подтверждения; история
   (`change_event`) не переписывается. Повторный скан не снимает подавление:
   это делает только аналитик.
3. **Вертикаль — словарный классификатор (FR-DT-10)** по 20-пунктной
   таксономии `reference/verticals.yaml` (ключевые слова на 7 языках).
   Голоса считаются по четырём источникам с разным весом: пути ссылок меню,
   schema.org (category / breadcrumb / имена позиций), title+meta, видимый
   текст (с потолком). Уверенность — доля победителя; без единого попадания
   вертикаль остаётся `unknown`, а не `other`. Без ML-модели: нет обучающей
   выборки, а словарь объясним аналитику и правится в YAML.
4. **Повторная детекция — из артефактов (FR-DT-12).** `detect.redetect`
   восстанавливает `PageSignals` из `manifest.json`, очищенного HTML и
   сетевых списков последних light/checkout-прогонов, применяет текущий
   (наложенный, ADR-0020) набор правил и сравнивает с сохранёнными
   строками. Dry-run по умолчанию; `--apply` обновляет найденное и пишет
   аудит, но **никогда не удаляет** исчезнувшие строки — они идут через
   подтверждения differ'а (ADR-0015), иначе одна ошибка в новом правиле
   стирала бы историю.
5. **Доступность — обычные change-события (FR-SC-05).** `store_offline`
   возникает при исчерпании бюджета ретраев e-commerce-домена (с id
   упавшего прогона), `store_online` — когда light-скан снова классифицирует
   домен как магазин. Сущность `store`, id = eTLD+1, поэтому события идут
   через историю, `changes` API и правила алертов. Списки и экспорты
   по-прежнему показывают только e-commerce-домены; недостижимые магазины
   видны в лентах изменений, чтобы клиент узнал об уходе.
