# ADR-0033 — Доля рынка из предрасчитанного снимка, а не из живой агрегации

Статус: принято (долг этапов 3–4, NFR-P-05). Связано: FR-API-03, FR-RP-03, LR-19, NFR-P-05, NFR-P-08.

## Контекст

`GET /v1/stats/market-share` считал ячейки (страна, платформа, провайдер)
при каждом запросе: выборка всех видимых в C1 магазинов (join `host`,
`domain`, `domain_source`, opt-out), join 1,5 млн строк `store_provider`,
`count(DISTINCT host_id)` по ячейке, второй проход для слияния редких
провайдеров в `other`. На стенде в 1 млн магазинов (4 vCPU, Postgres 16,
`work_mem` 4 МБ) это 13 с для одной страны и 45 с без фильтра; с
`work_mem` 256 МБ и 4 параллельными воркерами — всё ещё 10 с
(`EXPLAIN ANALYZE`: сортировка 1,5 млн строк для DISTINCT доминирует).
Порог ТЗ — p95 ≤ 3 с. Никакая настройка Postgres не даёт запас в 3×.

Данные меняются с темпом сканов (дни), а не запросов; `min_cell`
(порог публикации ячейки, 30) — настройка сервера, не параметр клиента.
Сегмент entitlement и фильтры запроса выбирают **целые ячейки** по стране
и платформе. Значит одна таблица ячеек обслуживает всех клиентов.

## Решение

- Таблица `market_share_cell` (миграция 0013): строка на (`role`, `country`,
  `platform_id`, `provider_id`) с числом магазинов; `role = NULL` — любая
  роль, отдельные срезы на каждую `ProviderRole`; `provider_id = NULL` —
  размер ячейки; `provider_id = 'other'` — число различных магазинов, у
  которых есть провайдер с числом магазинов < `min_cell` в этой ячейке
  (слияние FR-RP-03 выполняется при пересчёте тем же `min_cell`).
- `payintel stats refresh` (`payintel.stats.snapshot.refresh`) пересчитывает
  все ячейки в одной транзакции (`DELETE` + `INSERT`), так что читатели видят
  либо прошлый, либо новый снимок. Пакетная работа: `SET LOCAL
  statement_timeout = '30min'`, `work_mem = '256MB'` только в этой
  транзакции. На стенде пересчёт 1 млн магазинов — 1 мин 28 с (8 срезов).
  Запуск из cron раз в час (runbook §14).
- API читает снимок (`read.market_share_snapshot`): скрывает ячейки
  < `min_cell`, отдаёт провайдеров ≥ `min_cell` и строку `other`;
  `as_of` в ответе — `computed_at` снимка, а не момент запроса. На стенде
  ответ 0,05–0,8 с вместо 13–45 с.
- Пока снимка нет (первое развёртывание до первого `refresh`), API
  агрегирует живым запросом, как раньше: корректность не зависит от cron,
  только скорость. Тест `test_market_share_snapshot_equals_live_aggregation`
  требует, чтобы оба пути давали одинаковые ячейки.

## Последствия

- Доля рынка отстаёт от сканов не более чем на период cron; `as_of`
  честно показывает это клиенту (FR-API-10 о методологии не меняется).
- Отчёты C (`reports.aggregates`) и экспорт `aggregate` продолжают считать
  из ClickHouse / живых таблиц: они строятся офлайн и нуждаются в помесячной
  динамике, которой в снимке нет.
- Изменение `report_min_cell_size` требует `payintel stats refresh`, иначе
  строка `other` соответствует старому порогу (ячейки и провайдеры
  фильтруются новым порогом сразу).
