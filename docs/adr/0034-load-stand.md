# ADR-0034 — Нагрузочный стенд NFR-P: синтетические данные и собственный нагрузчик

Статус: принято (долг этапов 1–4, AC-12). Связано: NFR-P-01…P-08, ADR-0002, ADR-0033.

## Контекст

Пороги раздела 7.1 ТЗ формулируются для 1 млн магазинов, k6/Locust и
серверов AX42/AX102. В среде разработки нет ни реальных магазинов, ни
этих инструментов (пакеты недоступны), ни серверов: 4 vCPU / 15 ГБ,
Postgres 16 в контейнере с настройками по умолчанию (`shared_buffers`
128 МБ, `work_mem` 4 МБ). Проверить пороги всё же нужно до первого
клиента, а не после.

## Решения

1. **Синтетический набор** `scripts/synth_dataset.py`
   (`payintel.bench.synthetic`): детерминированный (seed) миллион
   магазинов с распределениями, похожими на ожидаемые (Zipf по 135
   провайдерам и 50 способам оплаты, 20 стран, 21 платформа, 40 %
   с Tranco-рангом, 30 % с событиями), все видимые в C1 (`ecommerce`, не
   CZDS, без opt-out), плюс организация `BENCH-0` с безлимитным
   entitlement `c1_full` и ключом. Загрузка через `COPY` батчами по 50 000
   (≈20 мин на 1 млн, 2,1 ГБ в Postgres). Генератор отказывается работать
   поверх существующих `store_profile` без `--reset`: это стенд, не
   продакшен. Данные не претендуют на реальные доли рынка — только на
   объём и форму.
2. **Нагрузчик** `scripts/bench_api.py` (`payintel.bench.api_load`): asyncio
   + httpx, открытый цикл (запросы стартуют по расписанию `t0 + i/rps`,
   независимо от ответов, поэтому очередь на сервере попадает в
   задержку), процентили nearest-rank, пороги из ТЗ, JSON-отчёт. k6/Locust
   недоступны; собственный код проверяется юнит-тестами.
3. **Нагрузка, где ТЗ её не задаёт.** P-03 — 20 rps по ТЗ (AS-14). Для
   P-04 и P-05 ТЗ даёт только порог: взяты 1 страница по 1 000 строк в
   секунду (1 000 записей/с = 86 млн записей в сутки, больше любой квоты
   FR-API-06) и 1 запрос доли рынка в секунду; оба со смесью фильтров
   (страна, платформа, провайдер, сортировки, сегмент).
4. **Что нашлось и исправлено** (без стенда не нашлось бы):
   - страница из 1 000 магазинов делала ≈6 000 запросов к Postgres и
     1 500 к ClickHouse (по строке): 11 с уже на 20 000 магазинов.
     `read.build_stores` собирает страницу фиксированным числом запросов
     (провайдеры, методы, PSP-хосты, последние изменения через оконную
     функцию, улики одним `LIMIT n BY` в ClickHouse);
   - `authenticate` писал `api_key.last_used_at` на каждом запросе внутри
     транзакции запроса — блокировка строки ключа выстраивала все
     параллельные запросы клиента за самым медленным (ожидание `UPDATE`
     до 25 с, часть запросов падала по `statement_timeout`). Теперь не
     чаще раза в минуту; точные времена есть в `usage_log`;
   - `payintel api serve --workers N` не запускался (uvicorn требует
     import-строку для нескольких процессов) — добавлена фабрика
     `payintel.api.runtime:application`;
   - доля рынка — ADR-0033 (снимок вместо живой агрегации).
5. **Prometheus (NFR-P-07).** `prometheus-client`; `GET /metrics` за
   токеном `secrets.metrics_token`; гистограммы запросов API и задержки
   скан → алерт, gauge возраста очереди алертов; экспортер в notifier
   (`--metrics-port`).

## Последствия

- Абсолютные числа стенда (4 vCPU, Postgres без настройки) ниже, чем
  будут на `app-1`; они зафиксированы в `docs/capacity.md` вместе с тем,
  что осталось проверить на реальном железе (NFR-P-01 на 100 тыс. доменов,
  NFR-P-02 за 24 ч).
- Стенд повторяем: `make bench-data`, `payintel stats refresh`,
  `payintel api serve --workers 2`, `make bench-api`. Прогоны не входят в
  CI (минуты и гигабайты), но код стенда покрыт тестами.
