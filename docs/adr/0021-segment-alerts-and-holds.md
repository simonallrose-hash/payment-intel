# ADR-0021 — Сегментные алерты без watchlist и удержание доставок при всплеске `provider_removed`

Статус: принято (этап 4). Связано: FR-AL-05, FR-QA-04, FR-AL-01…04, ADR-0019.

## Решения

1. **Правило без watchlist = весь сегмент гранта.** Правило алерта может не
   ссылаться на watchlist; тогда оно срабатывает для всех магазинов
   сегмента организации (entitlement) и может быть сужено списком стран и
   платформ. Сужение валидируется против гранта при сохранении: страна или
   платформа вне сегмента отклоняется (422), а не «тихо» игнорируется.
   Matcher применяет те же `c1_visible`-ограничения, что и API, поэтому
   сегментный алерт не может сообщить о домене вне сегмента.
2. **Всплеск `provider_removed` — качество, а не событие.** Если за 24 ч
   число `provider_removed` для одного провайдера превышает
   `anomaly_removed_multiplier` (3×) среднесуточного за предыдущие 7 дней
   и не меньше `min_events`, поднимается quality-алерт
   `provider_removed_spike` для `staff_analyst`, а клиентские доставки по
   этому провайдеру удерживаются (`delivery.held_by_alert_id`,
   `next_attempt_at = NULL`). Удержание — на уровне доставки, не правила:
   остальные события клиента уходят как обычно.
3. **Разблокирует только аналитик.** Подтверждение всплеска
   (`confirm`) освобождает доставки, отклонение (`discard`) переводит их в
   `failed` с заметкой; обе операции — в аудите. Автоматического
   «размораживания» по таймеру нет: ложное массовое `provider_removed`
   (сломанное правило, сбой скана) дороже задержки уведомления.
4. **Детектор — в воркере алертов** (`quality.anomalies`, запуск перед
   каждой диспетчеризацией и по `payintel quality anomalies`), без
   отдельного планировщика.
