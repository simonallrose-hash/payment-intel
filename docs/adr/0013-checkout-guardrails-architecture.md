# ADR-0013: Архитектура guardrails чекаута

Статус: принято (этап 2, 2026-10-08)

## Контекст

FR-CW-04, AS-20, AS-21 и LR-03 требуют, чтобы проход до чекаута физически не
мог нажать кнопку оплаты/заказа, ввести реальные карточные данные, решить
CAPTCHA, отметить рассылку или войти в чужой аккаунт — при любом адаптере,
любой эвристике и любой ошибке в их коде. ТЗ описывает результат (AC-04:
1 000 прогонов магазина-ловушки без запрещённых действий), но не механизм.

## Решение

Четыре независимых слоя, каждый из которых достаточен сам по себе:

1. **`ClickPolicy`** (Python, `guardrails/policy.py`). Единственный вход для
   любого клика — `GuardedPage.click(locator, purpose)`. Перед кликом
   элемент описывается (`DESCRIBE_CONTROL_JS`: текст, `aria-label`, `value`,
   `title`, `alt`, `name`, `id`, классы, `data-*`, `href`, форма-родитель) и
   решается по словарю `reference/checkout_dictionary.yaml` на 10 языках:
   - фраза финального действия («Place order», «Zahlungspflichtig bestellen»,
     «Commander», «Zamawiam i płacę» …) или бренд оплаты в любом из полей —
     `FINAL_ACTION`, никогда не кликается;
   - маркер в атрибутах (`place_order`, `checkout-submit`, `btn-pay` …) или
     `type=submit` внутри формы заказа/оплаты — `FINAL_ACTION`;
   - текст не из списка нужной цели (`step_actions`, `add_to_cart`,
     `guest_words` …), пустой текст, `disabled` — `AMBIGUOUS`, не кликается,
     остановка `guardrail_ambiguous_button`.
   Разрешается только явное совпадение с фразой нужной цели. Property-тест
   (hypothesis, 3 000 примеров) мутирует финальные фразы (регистр, пробелы,
   вложенные теги, суффиксы, слоты `text/aria/value/title/alt`) — ни одна
   не разрешается.
2. **Init-script в браузере** (`guardrails/injection.py`). Ставится через
   `context.add_init_script` до скриптов страницы: capturing-слушатели
   `submit` и `click` отменяют отправку форм заказа и клики по финальным
   элементам, даже если их инициировал JavaScript магазина;
   `HTMLFormElement.submit()`/`requestSubmit()` обёрнуты тем же правилом;
   в фазе захвата (`phase=capture`) отменяется отправка *любой* формы.
   Отменённые попытки собираются в `window.__payintel.blocked` и попадают
   в журнал прохода. Скрипт только добавляет слушатели — отпечаток браузера
   не меняется (AS-20).
3. **Маршрутизатор запросов** (`context.route("**/*")`): `POST/PUT/PATCH/DELETE`
   на URL с маркером заказа (`/checkout/order`, `wc-ajax=checkout`,
   `/payment/authorize` …) обрываются (`blockedbyclient`); цели во
   внутренних/приватных сетях — тоже (NFR-S-09). Маркеры проверяются по
   пути и query, а не по имени хоста: магазин `payment-shop.de` не должен
   терять корзину.
4. **Отсутствие методов.** У `GuardedPage` нет `page.evaluate` с
   произвольным вводом для адаптеров, нет ввода CAPTCHA, нет работы с
   чекбоксами кроме `tick_required` (только `required` чекбоксы, и только
   если их текст не про рассылку/маркетинг по словарю `newsletter_words`),
   нет ввода учётных данных кроме собственного системного аккаунта
   (`fill_credential` проверяет, что e-mail — адрес пробы).

Магазин-ловушка `tests/fixtures/shops/trap_shop` содержит финальные кнопки на
10 языках, кнопки-обманки с нейтральным текстом внутри формы заказа,
`type=button` с `requestSubmit()`, скрытые рассылочные чекбоксы, CAPTCHA и
ссылку входа в чужой аккаунт; сервер считает каждое запрещённое действие.
Прогон ×1 000 (`PAYINTEL_TEST_TRAP_RUNS=1000`) — критерий AC-04.

## Последствия

- Любая новая возможность адаптера проходит через `GuardedPage`; «сырой»
  `Page` адаптерам не выдаётся.
- Цена консервативности: кнопки с нестандартным текстом не нажимаются и
  дают `guardrail_ambiguous_button`; еженедельный разбор стопов (FR-QA-06)
  пополняет словарь `step_actions`, а не ослабляет политику.
- Пере-рендер страницы через `document.open()` переустанавливает слушатели
  (патч `Document.prototype.open`); `page.set_content` в тестах — тоже.
