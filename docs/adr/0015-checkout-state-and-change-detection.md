# ADR-0015: Текущее состояние по чекауту и детекция изменений

Статус: принято (этап 2, 2026-10-08)

## Контекст

FR-DT-05/06 вводят `active_on_checkout` и `acquirer_hidden`, FR-DT-11 — сторонние
хосты страницы оплаты, FR-HI-02…04 — материализацию `store_*` и события
изменений с правилом «два подряд». ТЗ не определяет, когда эквайер считается
скрытым, что делать со строкой, которую два скана подряд не видят, какие
запросы относятся к «странице оплаты», и чей сигнал о платформе главнее.

## Решение

1. **`acquirer_hidden = true`**, если проход дошёл до шага оплаты, среди
   активных провайдеров есть оркестратор (роль `orchestrator`) или на шаге
   обнаружен токенайзер, и ни один активный провайдер не имеет роли
   `gateway`. Значение пересчитывается только успешными проходами; `blocked`,
   `timeout`, `error` его не меняют.
2. **Правило «два подряд».** Сущность (провайдер, метод, сторонний хост)
   появляется в `store_*` после первого скана с `confirmations=1`;
   событие `*_added` пишется, когда второй подряд скан её подтверждает.
   Отсутствие увеличивает `misses`; при `misses ≥ 2` пишется `*_removed` и
   строка **удаляется** из текущего состояния (история остаётся в
   ClickHouse). Сканы со статусом `blocked`/`timeout`/`error` и не дошедшие
   до шага оплаты ничего не подтверждают и не считают пропуском: раз страница
   оплаты не наблюдалась, отсутствие не доказано. Строки лёгкого скана (`low`,
   без `active_on_checkout`) подтверждаются и «пропускаются» теми же
   счётчиками.
3. **Сторонние хосты (FR-DT-11)** — все запросы браузера с момента входа в
   шаг «чекаут», в любом фрейме (iframe токенайзера — тоже), сгруппированные
   по хосту; категория и `provider_id` — из `reference/host_categories.yaml`
   и правил `network_host`/`script_src`. Хосты главной и товара не
   считаются: они описывают витрину, а не оплату.
4. **Платформа.** Лёгкий скан (главная, `generator`, плагины) — авторитет;
   проход по чекауту перезаписывает `platform_id` только при отсутствии
   профиля или при уверенности не ниже текущей. Дифф сравнивает находку с
   профилем *до* применения скана, поэтому `platform_changed` возможен.
5. **Адаптер** выбирается по `store_profile.platform_id`, а при его
   отсутствии — правилами платформ по главной (ADR-0014 п. 8).
6. **`store_offline`/`store_online`** на этапе 2 не генерируются: они
   требуют согласованного определения «магазин недоступен» (N неудач подряд
   лёгкого скана и DNS), которое вводится вместе с FR-SC-05 в планировщике
   этапа 3. Типы событий в схеме есть.
7. **Профиль без ClickHouse (NFR-R-06).** `history/read.py::read_store` собирает
   состояние только из PostgreSQL (`store_profile`, `store_provider`,
   `store_payment_method`, `store_checkout_host`, последние `change_event`);
   ClickHouse нужен для истории и агрегатов, но не для ответа API.

## Последствия

- Первый проход никогда не даёт событий; клиентские алерты (этап 3)
  опираются на `change_event`, поэтому «ложные» появления от одного шумного
  скана исключены ценой задержки в один цикл (7–30 дней).
- Удаление строки при двух пропусках означает, что повторное появление
  через три скана снова начнётся с `confirmations=1`; это осознанно: для
  клиента важна актуальность, а не непрерывность строки.
