# ADR-0014: Решения по проходу до чекаута

Статус: принято (этап 2, 2026-10-08)

## Контекст

FR-CW-02…14 задают последовательность «главная → товар → корзина → чекаут →
шаг оплаты», лимиты (90 с, 1 ГБ, перезапуск каждые 50 проходов) и правила
безопасности, но оставляют открытыми: что считать товаром, как разрешать
«стену входа», когда вводить тестовые значения оплаты, чем измерять память,
какой статус у прохода, прерванного дедлайном.

## Решение

1. **Товар.** Кандидаты — ссылки по селекторам адаптера, затем эвристики
   (`/product/`, `/p/`, `/artikel/`, `/produit/` …, кроме служебных путей),
   не более трёх; товар подтверждается наличием контроля «в корзину» на
   странице. Варианты выбираются первым доступным значением. Три неудачи —
   `product/no_product_found`.
2. **Стена входа** разрешается в порядке: поля адреса уже видны (гость /
   одностраничный чекаут) → контроль «как гость» → вход существующим
   системным аккаунтом → регистрация (FR-CW-12, флаг
   `allow_account_registration`, только когда гостевого варианта нет) →
   `checkout/guest_unavailable_registration_disabled`. Без ключа шифрования
   (`PAYINTEL_SECRETS__ENCRYPTION_KEY`) регистрация отключена: пароль
   нельзя сохранить по FR-CW-12.
3. **Тестовые значения оплаты** (FR-CW-14, ADR-0003) вводятся только если
   шаг оплаты не раскрыл ни одного способа сам и обнаружен документированный
   токенайзер (Stripe Elements, Adyen, Braintree, Checkout.com, Mollie,
   Square, generic `cc-*`). Кнопка оплаты не нажимается никогда; результат
   — `methods_revealed` и журнал `payment_fill_summary`.
4. **Дедлайн 90 с** — `navigation/timeout` со `coverage` по самому дальнему
   начатому шагу (`ScanRun.coverage` ≠ шаг стопа); прерванный шаг попадает
   в `steps` с фактической длительностью. Свидетельства (скриншот, DOM)
   снимаются с лимитом 3 с, чтобы висящая навигация не задержала выход.
5. **Память** — `JSHeapUsedSize` страницы через CDP `Performance.getMetrics`
   после каждой навигации; превышение `context_memory_limit_mb` —
   `navigation/memory_limit`. RSS процесса Chromium общий для всех
   контекстов воркера и как метрика на проход не годится.
6. **Перезапуск браузера** каждые `browser_restart_every_walks` проходов
   ждёт закрытия контекстов в полёте: перезапуск «посреди» параллельных
   проходов закрывал их страницы (28 обрывов из 1 000 в первом прогоне
   ловушки).
7. **Favicon** читается через `context.request` из Python, а не `fetch` в
   странице: Chromium объединяет запрос `/favicon.ico` со своим собственным
   запросом иконки вкладки, и под перехватом он не доходит до маршрутизатора.
8. **Платформа без профиля.** Если у магазина ещё нет лёгкого скана,
   адаптер выбирается правилами платформ по HTML главной (тот же движок,
   `page_type=homepage`); иначе — из `store_profile.platform_id`.
9. **Навигации только внутри eTLD+1 магазина** и по `robots.txt`: `goto` на
   чужой хост или запрещённый путь — `navigation/navigation_error` /
   `navigation/robots_disallowed`. Редиректы на хостед-страницы PSP не
   нужны: проход заканчивается на шаге оплаты.
10. **Egress.** Браузер резолвит имена сам; приватные/loopback-адреса и
    внутренние имена отсекаются маршрутизатором по имени хоста и по IP в
    URL. Остаточный риск DNS-rebinding (TOCTOU между проверкой и
    соединением) признаётся: воркеры чекаута живут в сети без доступа к
    внутренним сервисам (NFR-S-09, compose `crawl-1`).

## Последствия

Проход консервативен: при сомнении он останавливается с кодом таксономии и
свидетельствами, а не «пробует ещё». Доля `other` и топ стопов разбираются
еженедельно (runbook §12); фикстуры `tests/fixtures/shops/` пополняются DOM-
снимками реальных стопов.
