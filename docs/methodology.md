# Методология (этапы 0–1)

Описывает то, что уже определено схемой и кодом; раздел про чекаут
дополняется на этапе 2.

## Сущности и роли

- `provider` — PSP, шлюз, оркестратор или BNPL-провайдер. Роли из ТЗ:
  `gateway`, `acquirer`, `orchestrator`, `bnpl`, `wallet`, `fraud_tool`,
  `3ds_sdk` (две последние — только для C1/C2).
- `payment_method` — таксономия 5.3: карты (по схеме), кошельки, BNPL,
  банковские переводы/редиректы, прямой дебет, наличные/ваучеры, локальные
  методы.
- `platform` — платформа магазина с иерархией (`woocommerce → wordpress`).
- `vertical` — 20 вертикалей.

## Правила детекции

Правило (`rules/**/*.yaml`): `id`, `version`, `target_type`, `target_id`,
`signal_type` (`network_host`, `script_src`, `js_global`, `html_pattern`,
`cookie`, `header`, `iframe_src`, `meta`, `sha256`), `pattern`, `weight` (0–1),
`page_scope`, `enabled`, `needs_verification`, `source` (ссылка на
официальную документацию), `note`.

Инварианты, проверяемые загрузчиком:
- `id` начинается с `{target_type}.{target_id}.`;
- `target_id` существует в справочнике (FR-NR-05);
- `enabled: true` несовместимо с `needs_verification: true`;
- регулярные выражения компилируются, хосты валидны, sha256 — 64 hex;
- версия ruleset = хеш содержимого всех правил; изменение паттерна без
  повышения `version` отклоняется при синхронизации.

Сигнатуры берутся только из официальной документации вендора (ADR-0004).
Всё, в чём нет уверенности, лежит как `enabled: false, needs_verification: true`
и перечислено в отчёте этапа.

## Сигналы лёгкого скана (FR-LS-05, FR-DT-02)

Сканер только собирает артефакты; детекция — чистая функция от них
(`detect.engine.match_page`), поэтому повторная детекция по сохранённым
артефактам (FR-DT-12) даёт тот же результат. Из страницы извлекаются:
`script_src`, `iframe_src`, `form_action`, внешние хосты, JS-глобалы из
inline-скриптов (`window.X`, `var X`), заголовки ответа, имена cookie,
HTML-паттерны, favicon (sha256), JSON-LD типы. Правило применяется только на
страницах своей `page_scope`.

Классификатор e-commerce (FR-DS-08) — взвешенная сумма сигналов из
`reference/ecommerce_signals.yaml`: платформа магазина (0.45), schema.org
`Product/Offer` (0.25), фразы «в корзину» (0.25), пути корзины/чекаута
(0.15/0.15), маркеры валют (0.05); ≥0.5 → `ecommerce`, <0.15 → `not_ecommerce`,
между — `candidate`. Парковка определяется по NS/CNAME из
`reference/parking_signatures.yaml` и по HTML-паттернам (плюс «заглушка»:
<1500 байт без ссылок).

## Уверенность (FR-DT-04, FR-DT-05)

Для каждой цели (провайдер, метод, платформа) берётся лучший вес по каждому
типу сигнала, сумма ограничена 1.0 (`confidence_score`). Уровень:
- `high` — сетевой сигнал (хост/iframe/форма) на странице чекаута, либо ≥2
  типов сигналов, один из которых на чекауте или платформа;
- `medium` — сигнал на чекауте, либо платформа с весом ≥0.7;
- `low` — остальное (в том числе всё, что найдено лёгким сканом без чекаута).

Лёгкий скан пишет провайдеров в `store_provider` как `low`, без
`active_on_checkout`; материализация никогда не понижает уверенность и не
снимает `active_on_checkout` — это делает только скан чекаута (этап 2) и
правило «два подряд» (`confirmations`/`misses`).

## Сигналы чекаута (FR-CW-07, FR-DT-02, FR-DT-05)

Проход до шага оплаты (этап 2) добавляет к сигналам лёгкого скана страницу
`page_type=payment_step`: скрипты, iframe и формы страницы, JS-глобалы
(`window.Stripe`, `window.adyen` …), все хосты сетевых запросов с момента
входа в чекаут (в любом фрейме), cookie, заголовки, favicon (sha256) и
видимые метки способов оплаты (`checkout_label`: текст, `alt`/`title`
логотипов, имена файлов). Провайдер, найденный на шаге оплаты, получает
`active_on_checkout=true`; найденный только на витрине — `false`.
`acquirer_hidden` — оркестратор или токенайзер на шаге оплаты без видимого
шлюза (ADR-0015).

Сторонние хосты страницы оплаты (`obs_checkout_host`, `store_checkout_host`)
категоризируются по `reference/host_categories.yaml` и правилам
`network_host`/`script_src`: `psp` (с `provider_id`), `analytics`, `ads`, `cdn`,
`tag_manager`, `session_replay`, `chat`, `unknown`. Для клиентов видны только
`psp` (AS-23).

## Изменения (FR-HI-03, FR-HI-04)

События `provider_added/removed`, `method_added/removed`,
`checkout_host_added/removed`, `platform_changed` пишутся по правилу «два
подряд»: появление подтверждается вторым успешным проходом, исчезновение —
двумя подряд проходами до шага оплаты без сущности. Проходы `blocked`,
`timeout`, `error` и не дошедшие до оплаты ничего не меняют. Первый проход
магазина событий не даёт (ADR-0015).

## Остановки (FR-CW-13)

Каждый проход, не дошедший до шага оплаты, пишет одну строку `obs_scan_stop`
с кодом из `reference/stop_reasons.yaml` (шаг × причина; `other` — на любом
шаге, с обязательным пояснением), длительностями шагов, URL, элементом и
ключами скриншота/DOM в S3. Код вне таксономии превращается в `other` с
исходным кодом в пояснении, так что разбор (FR-QA-06) всегда полный.
Статус `scan_run.status` выводится из шага и причины (например,
`checkout/login_failed` → `login_required`, `*/timeout` → `timeout`);
`coverage` — самый дальний начатый шаг.

## Страна магазина (FR-DT-09)

Взвешенное голосование по `reference/country_signals.yaml`: ccTLD (0.35),
адрес в schema.org (0.30), валюта (0.20), телефонный код (0.20), язык
(0.15), hreflang (0.10), страна хостинга (0.05, только если известна).
`high` — лидер ≥0.5 и доля ≥60 %; `medium` — лидер ≥0.2 с отрывом ≥0.1;
иначе `low`. Страна не выдумывается: без сигналов поле остаётся пустым.

## Gold set и метрики (FR-QA-01/02)

Gold set — ручная разметка по домену: `present=true|false` для провайдера,
метода, платформы и страны. Разметка никогда не генерируется кодом
(ADR-0006); в репозитории только синтетическая выборка `*.example` для
тестов метрик.

Метрики: по типу сущности и по правилу.
- provider / payment_method — множественные метки: TP, FP, FN по парам
  (домен, сущность); отрицательные метки (`present=false`) превращают
  предсказание в FP.
- platform / country — единственное значение на домен.
- precision = TP/(TP+FP), recall = TP/(TP+FN), F1 — гармоническое среднее.
- Per-rule метрики читаются из ClickHouse (`obs_provider`, `obs_payment_method`,
  `obs_tech`): правило → сколько его срабатываний подтверждено разметкой.
- Gate: precision по PSP ≥ 0.95 (настройка `quality.min_psp_precision`);
  пустой gold set → «not applicable», релиз не блокируется, но и не
  подтверждается.

## Ограничения сканера (неизменяемые)

Не нажимать кнопки оплаты/заказа; не вводить реальные платёжные данные;
только значения из `reference/test_payment_values.yaml` под
`allow_payment_field_fill`; регистрация только по FR-CW-12 под флагом; без
CAPTCHA, stealth и ротации IP; соблюдение robots.txt; собственный User-Agent
`PayIntelBot/1.0 (+<страница бота>)`. Лёгкий скан не запрашивает
страницы чекаута, не выполняет JavaScript и не отправляет формы; проход по
чекауту (этап 2) идёт только через `GuardedPage` с политикой кликов на 10
языках, DOM-перехватчиком и маршрутизатором запросов (ADR-0013); магазин-
ловушка ×1 000 без единого запрещённого действия — критерий AC-04.
Egress-фильтр (NFR-S-09) и санитайзер PII (FR-LS-04) — общие для обоих
сканеров.

## Поля C1 (AS-23)

`store_profile.platform_version`, `obs_tech.version`, категории сторонних
хостов кроме платёжных, роли `fraud_tool`/`3ds_sdk` — внутренние. Они не
входят в клиентские Pydantic-схемы ответов и выгрузок (этап 3, тест AC-07).
